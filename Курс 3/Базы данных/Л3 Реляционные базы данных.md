#### Реляционный подход к организации баз данных

В настоящее время реляционный подход более распространённый.

**Преимущества**: наличие небольшого набора абстракций, которые позволяют проще моделировать распространённые предметные области, наличие простого, но мощного математического аппарата из теории множеств и математической логики, возможность манипулирования данными без необходимости знания конкретной физической организации базы данных во внешней памяти.
**Недостатки**: ограниченность в нетрадиционных областях (тех или иных областей, в которых плоские таблицы не пригодны, например в системах автоматизации проектирования, машиностроения и др.)

Прототипы реляционных СУБД появились в 70-х и в середине 80-х они уже вытеснили ранние СУБД.
#### Базовые понятия реляционного подхода

**Тип данных** - в реляционной модели смысл типа данных такой же как в языках программирования.

**Домен** - специфичное для баз данных понятие похожее на подтипы данных в языках программирования (включая пользовательские типы). Допустимое потенциальное множество значений данного типа. 

**Атрибут** - одна из характеристик объекта, хранимого в базе данных.

**Схема отношения** (Шапка/Структура таблицы) - именованное множество пар: имя атрибута, имя домена или типа данных.

**Степень/арность схемы отношения** - мощность этого множества - количество элементов в схеме.

**Схема базы данных** - набор именованных схем отношений.

**Кортеж** (соответствующие данные схеме отношения) (запись) (строка в таблице) - множество пар `[имя атрибута, значение]`, которое содержит одно вхождение каждого имени атрибута, принадлежащего схеме отношения.

**Отношение** - множество кортежей, соответствующих одной схеме отношения. Есть _отношение-схема_ - заголовок отношения (шапка) и _отношение-экземпляр_ - набор кортежей (тело отношения) (совокупность записей).

**Реляционная база данных** - набор отношений, имена которых совпадают с именами схем отношений в схеме базы данных. (Совокупность связанных таблиц).
#### Фундаментальные свойства отношений

- Отсутствие кортежей-дубликатов (нет копий) - возникло из определения: *"отношения это множество кортежей"*. В классике утверждается, что *"каждое множество состоит из различных элементов"*. В каждом отношении есть первичный ключ, обеспечивающий это свойство. **Первичный ключ** - набор атрибутов, значения которых однозначно определяет кортеж отношение. Пример: ФИО могут совпадать, поэтому нужно применить все возможные атрибуты. Выбор атрибута важен. Понятие ключа важно для целостности БД.
- Кортежи не отсортированы. Уточнение: не обязаны быть отсортированы. Следует из определения отношения - множество кортежей - это отношения. Роль %%унр%% списков - пример %%трунь%% - было 100, все различаются по алфавиту, поэтому взяли сначала 21 и ещё.
- Отсутствие упорядоченности атрибутов, то есть **схема отношения**. Схема отношения это множество пар - имя атрибута и имя домена. ФИО, улица, дом, квартира. Алфавитный порядок этих атрибутов будет неудобен в использовании. Снова про ключ - может быть в любом месте атрибутов (но первый всегда id).
- Атомарность значений атрибутов.

**Домен** - потенциальное множество простого типа данных. Среди значений домена не могут содержаться множества значений. Например: столбик ФИО плохо, т.к. он содержит сразу три атрибута. Столбец даты также лучше разбить на день и месяц (INTEGER и STRING соответственно).
#### Декомпозиция базы данных

Это свойство обеспечивается процессом нормализации баз данных в частности первой нормальной формой (атомарные атрибуты).
#### Структура реляционных баз данных

Реляционная модель данных предложена человеком Дейт и состоит из 3-х частей:
- Структурная. Зафиксировать что единая структура данных в базе данных является нормализованным унарным отношением.
- Манипуляционная. Два фундаментальных механизма реляционных баз данных:
	- Реляционная алгебра исчисляется на теории множеств
	- Исчисления - классический логический аппарат, исчисления предикат первого порядка.
- Целостная часть - зафиксированы два основных требования целостности:
	- Целостность сущностей - любой кортеж любого отношения отличим от любого другого кортежа этого отношения
	- Целостность по ссылкам - в ходе нормализации сущности реального мира будут представлены в виде нескольких кортежей и нескольких отношений.
#### Базисные средства манипулирования реляционными данными

Реляционная алгебра впитала в себя из теории множеств теоретико-множественные операции:
- объединение множеств;
- пересечение множеств (отношений);
- разность отношений;
- произведение отношений;
- специальные реляционные операции:
	- ограничение отношения;
	- проекция отношения;
	- соединение отношений;
	- деление отношений;
- операции присваивания;
- операция переименования атрибутов.

Для формулировки запроса средствами реляционной алгебры пишут алгебраическое выражение, в котором чётко формулируют последовательность шагов выполнения запроса. Тот же запрос средствами реляционного счисления будет содержать лишь характеристики результирующего отношения, но без указания способа его формирования. Алгебраическая формулировка считается процедурной (императивной), а вот втором случае формулировка запроса описательная (декларативный).
#### Проектирование реляционных баз данных

При проектировании баз данных решается две основные проблемы:
- как отобразить объекты предметной области в абстрактной объектной модели данных (решается проблема логического проектирования базы данных);
- как обеспечить эффективное выполнение запросов в базе данных, то есть как расположить данные во внешней памяти и создание каких дополнительных структур (например индексов) потребовать;

Проектирование производится методом последовательных приближений к удовлетворительному набору схем отношений. Процесс проектирования - это процесс нормализации схем отношений, где каждая следующая нормальная форма обладает свойствами лучшими, чем предыдущие.

**Нормализация** – это разбиение таблицы на две или более, обладающих лучшими свойствами при включении, изменении и удалении данных. Окончательная цель нормализации сводится к получению такого проекта БД, в котором каждый факт появляется лишь в одном месте, т.е. исключена избыточность информации. Это делается не столько с целью экономии памяти, сколько для исключения возможной противоречивости хранимых данных.

Цели нормализации:
- Экономия памяти
- Уменьшение избыточности информации
- Упрощение управления данными
- Исключение противоречивости

Проблемы ненормализованных таблиц:
- Избыточность данных
- Аномалии обновления
- Аномалия удаления
- Аномалия ввода

В теории реляционных баз данных имеются следующие нормальные формы:
- Первая нормальная форма
- Вторая нормальная форма
- Третья нормальная форма
- Нормальная форма Бойса-Кодда
- Четвёртая нормальная форма
- Пятая нормальная форма (Нормальная форма проекции погружения)

Основные свойства нормальных форм:
- Каждая следующая нормальная форма в некотором смысле лучше предыдущей
- При переходе к следующей нормальной форме свойства предыдущих форм сохраняются

**Пример** - нормализация предметной области сотрудника организации:
- Сперва строится ненормализованная таблица:

| Фамилия | Имя | Отчество | Дата рождения | Адрес | Телефоны | Должность | Разряд | Зарплата | Дата приёма | Дата увольнения |
| ------- | --- | -------- | ------------- | ----- | -------- | --------- | ------ | -------- | ----------- | --------------- |
|         |     |          |               |       |          |           |        |          |             |                 |

**Первая нормальная форма** - значения атрибутов отношения должны быть атомарными.

- Таблица в первой нормальной форме:

| Фамилия | Имя | Отчество | Дата рождения | Улица | Дом | Квартира | Телефон 1 | Телефон 2 | Должность | Разряд | Зарплата | Дата приёма | Дата увольнения |
| ------- | --- | -------- | ------------- | ----- | --- | -------- | --------- | --------- | --------- | ------ | -------- | ----------- | --------------- |
|         |     |          |               |       |     |          |           |           |           |        |          |             |                 |

**Вторая нормальная форма** - отношение находится во второй нормальной форме в том и только том случае, когда это отношение находится в первой нормальной форме и каждый неключевой атрибут полностью зависит от первичного ключа. (Неключевой - не входящий в состав первичного ключа).

- Таблица во второй нормальной форме:
  Предлагается таблицу сотрудников разбить на две: сотрудники и физические лица. В одной будут сведения о сотрудниках как о работниках, вокруг атрибута первичного ключа код сотрудника и сведения о нём как о физическом лице с первичным ключом - код физического лица (в таблице сотрудники он будет внешним ключом).

| Код сотрудника | Код физического лица | Должность | Разряд | Зарплата | Дата приёма | Дата увольнения |
| -------------- | -------------------- | --------- | ------ | -------- | ----------- | --------------- |
|                |                      |           |        |          |             |                 |

| Код физического лица | Фамилия | Имя | Отчество | Дата рождения | Улица | Дом | Квартира | Телефон 1 | Телефон 2 |
| -------------------- | ------- | --- | -------- | ------------- | ----- | --- | -------- | --------- | --------- |
|                      |         |     |          |               |       |     |          |           |           |

Атрибут код физического лица является первичным ключом для таблицы "физические лица" и внешним для отношения "сотрудники".
#### Третья нормальная форма

Отношение находится в третьей нормальной форме тогда и только тогда, когда отношение находится во второй форме и каждый неключевой атрибут не транзитивно зависит от первичного ключа.

Таблица сотрудники разбивается на: сотрудники, должности и физические лица.


| Код сотрудника | Код физлица | Код должности | Дата приёма | Дата увольнения |
| -------------- | ----------- | ------------- | ----------- | --------------- |
|                |             |               |             |                 |

| Код должности | Наименование должности | Разряд | Заработная плата |
| ------------- | ---------------------- | ------ | ---------------- |
|               |                        |        |                  |

| Код физического лица | Фамилия | Имя | Отчество | Дата рождения | Улица | Дом | Квартира | Телефон 1 | Телефон 2 |
| -------------------- | ------- | --- | -------- | ------------- | ----- | --- | -------- | --------- | --------- |
|                      |         |     |          |               |       |     |          |           |           |
На практике третья нормальная форма схем отношений в большинстве достаточна. И приведением к ней процесс проектирования реляционной базы данных обычно заканчивается.
#### Семантическое проектирование реляционных баз данных

Проектирование реляционных баз сложный и неудобный для проектировщика процесс:
- Модель не предоставляет достаточных средств для представления смысла данных для семантического проектирования;
- Для многих приложений трудно моделировать предметную область на основе плоских таблиц;
- Хотя весь процесс проектирования происходит на основе учёта зависимостей, реляционная модель не предоставляет наглядных средств для отображения этих зависимостей.

Была предложена ER-модель (Entity Relationship, модель сущность-связь) - 1976 год Чен. 

Строится на таких понятиях как: сущность, связь, атрибут.
