#### Реляционный подход к организации баз данных

В настоящее время реляционный подход более распространённый.

**Преимущества**: наличие небольшого набора абстракций, которые позволяют проще моделировать распространённые предметные области, наличие простого, но мощного математического аппарата из теории множеств и математической логики, возможность манипулирования данными без необходимости знания конкретной физической организации базы данных во внешней памяти.
**Недостатки**: ограниченность в нетрадиционных областях (тех или иных областей в которых плоские таблицы не пригодны, например в системах автоматизации проектирования, машиностроения и др.)

Прототипы реляционных СУБД появились в 70-х и в середине 80-х они уже вытеснили ранние СУБД.
#### Базовые понятия реляционного подхода

**Тип данных** - в реляционной модели смысл типа данных такой же как в языках программирования.

**Домен** - специфичное для баз данных понятие похожее на подтипы данных в языках программирования (включая пользовательские типы). Допустимое потенциальное множество значений данного типа. 

**Аттрибут** - одна из характеристик объекта, хранимого в базе данных.

**Схема отношения** (Шапка/Структура таблицы) - именованное множество пар: имя атрибута, имя домена или типа данных.

**Степень/арность схемы отношения** - мощность этого множества - количество элементов в схеме.

**Схема базы данных** - набор именованных схем отношений.

**Кортеж** (соответствующие данные схеме отношения) (запись) (строка в таблице) - множество пар `[имя атрибута, значение]`, которое содержит одно вхождение каждого имени атрибута, принадлежащего схеме отношения.

**Отношение** - множество кортежей, соответствующих одной схеме отношения. Есть _отношение-схема_ - заголовок отношения (шапка) и _отношение-экземпляр_ - набор кортежей (тело отношения) (совокупность записей).

**Реляционная база данных** - набор отношений, имена которых совпадают с именами схем отношений в схеме базы данных. (Совокупность связанных таблиц).
#### Фундаментальные свойства отношений

- Отсутствие кортежей-дубликатов (нет копий) - возникло из определения: *"отношения это множество кортежей"*. В классике утверждается что *"каждое множество состоит из различных элементов"*.
- В каждом отношении есть первичный ключ, обеспечивающий первое свойство. **Первичный ключ** - набор аттрибутов, значения которых однозначно определяет кортеж отношение. Пример: ФИО могут совпадать, поэтому нужно применить все возможные аттрибуты. Выбор аттрибута важен. Даже %%возрат%% подойдёт - %%выбирать маленький по памяти%%. Понятие ключа важно для целостности БД.
- Кортежи не отсортированы. Уточнение: не обязаны быть отсортированы. Следует из определения отношения - множество кортежей это отношения. Роль %%унр%% списков - пример %%трунь%% - было 100, все различаются по алфавиту, поэтому взяли сначала 21 и ещё.
- %%Отс.%% упорядочности аттрибутов, то есть **схема отношения**. Схема отношения множество нар. - имя аттрибута и имя домена. ФИО, улица, дом, квартира. При алфавитном порядке этих аттрибутов будет неудобен в использовании. Снова про ключ - может быть в любом месте аттрибутов (но первый всегда id).
- Атомарность значений аттрибутов.

**Домен** - потенциальное множество простого типа данных. Среди значений домена не могут содержаться множества значений. Например: столбик ФИО плохо, т.к. он содержит сразу три аттрибута. Столбец даты также лучше разбить на день и месяц (INTEGER и STRING соответственно).
#### %%Пролящинит%% базы данных

Это свойство обеспечивается процессом нормализации баз данных в часности первой нормальной формой (атомарные аттрибуты).
#### Структура реляционных баз данных

Реляционная модель данных предложена человеком Дейт и состоит из 3-х частей:
- Структурная. Зафиксировать что единая структура данных в базе данных является нормализованным унарным отношением.
- Манипуляционная. Два фундаментальных %%манин%% реляционных баз данных:
	- Реляционная алгебра исчисляется на теории множеств
	- Исчисления - классический логический аппарат, исчисления предикат первого порядка.
- Целостная часть - зафиксированы два основных требования целостности:
	- Целостность сущностей - любой кортеж любого отношения отличим от любого другого кортежа этого отношения
	- Целостность по ссылкам - в ходе нормализации сущности реального мира будут представлены в виде нескольких кортежей и нескольких отношений.
#### Базисные средства манипулирования реляционными данными

Реляционная алгебра впитала в себя из теории множеств теоретико-множественные операции:
- объединение множеств;
- пересечение множеств (отношений);
- разность отношений;
- произведение отношений;
- специальные реляционные операции;
- ограничение отношения;
- проекция отношения;
- соединение отношений;
- деление отношений;
- операции присваивания;
- операция переименования аттрибутов.

Для формулировки запроса средствами реляционной алгебры пишут алгебраическое выражение в котором чётко формулируют последовательность шагов выполнения запроса. Тот же запрос средствами реляционного счисления будет содержать лишь характеристики результирующего отношения, но без указания способа его формирования. Алгебраическая формулировка считается процедурной (императивной), а вот втором случае формулировка запроса описательная (декларативный).
#### Проектирование реляционных баз данных

При проектировании баз данных решается две основные проблемы:
- как отобразить объекты предметной области в абстрактной объектной модели данных (решается проблема логического проектирования базы данных);
- как обеспечить эффективное выполнение запросов в базе данных, то есть как расположить данные во внешней памяти и создание каких дополнительных структур (например индексов) потребовать;

Проектирование производится методом последовательных приближений к удовлетворительному набору схем отношений. Процесс проектирования это процесс нормализации схем отношений, где каждая следующая нормальная форма обладает свойствами лучшими, чем предыдущие.

#### Семантическое проектирование реляционных баз данных

Проектирование реляционных баз сложный и неудобный для проектировщика процесс:
- Модель не предоставляет достаточных средств для представления смысла данных для семантического проектирования;
- Для многих приложений трудно моделировать предметную область на основе плоских таблиц;
- Хотя весь процесс проектирования происходит на основе учёта зависимостей;
- Реляционная модель не предоставляет наглядных средств для отображения этих зависимостей.
